# Арена переговоров — динамический maker, версия 0.4.0

React SPA теперь работает через серверный API с PostgreSQL. Браузер не подключается к базе напрямую. Пароли базы находятся только в `.env` на сервере.

Реализованы регистрация и вход, сохранение профиля, каталог из базы, личные попытки, история ответов, результаты, отзывы, черновики редактора, публикация версий и архивирование сценариев. При перезапуске тренировки старая попытка остаётся в истории. Старый результат всегда использует ту версию вопросов, по которой пользователь проходил тренировку.

В исходном архиве один исполняемый сценарий: `terms` («Переговоры об условиях работы»). `new-deadline` и `feedback` — демонстрационные макеты. Они также хранятся в PostgreSQL, но реальные оценки для них не придуманы. Новые сценарии создаются на пустом полотне или копированием существующего сценария. При открытии старых сценариев maker использует адаптер; исходные опубликованные версии не меняются.

## Обновление существующего проекта

Завершены четыре этапа MVP: модель `reactions / intent / examples`, полотно React Flow, Inspector и редактирование графа, проверка и тестовое прохождение. Список возможностей и устройство кода — в [docs/MAKER.md](docs/MAKER.md).

Остановите старое приложение. Распакуйте исходники новой версии в отдельную папку и перенесите туда свой `.env`. В этой папке выполните:

```powershell
npm ci
npm run db:migrate
npm run dev
```

Используется существующая база. Миграция `002_scenario_editor.sql` добавляет поле `editor` в черновики; пользователи, попытки, сценарии и опубликованные версии сохраняются. Пересоздавать базу или повторно назначать администратора не нужно. Если база новая, выполните полную настройку ниже.

Администратор открывает `/admin/scenarios`, создаёт пустой сценарий или копию и попадает в maker. Старые ссылки `/editor/:scenarioId` также работают.

## Запуск на Windows с установленным PostgreSQL

Потребуются Node.js **22.12+** (рекомендуется 24) и PostgreSQL **16+**. Все команды npm запускайте из папки, содержащей `package.json`.

1. Откройте SQL Shell (psql) или Query Tool в pgAdmin под администратором PostgreSQL. Создайте отдельного пользователя приложения и базу:

```sql
CREATE ROLE arena WITH LOGIN PASSWORD 'change_me';
CREATE DATABASE arena OWNER arena;
```

Замените `change_me` своим паролем. `CREATE DATABASE` выполняйте отдельно от транзакции. Если база и пользователь уже существуют, повторно создавать их не нужно.

2. В PowerShell, в папке проекта:

```powershell
Copy-Item .env.example .env
npm ci
```

Откройте `.env` и задайте свою строку подключения. Там же можно настроить первого администратора:

```dotenv
DATABASE_URL=postgresql://arena:change_me@127.0.0.1:5432/arena

ADMIN_NAME=Administrator
ADMIN_EMAIL=admin@example.com
ADMIN_PASSWORD=change_me_admin
```

`ADMIN_*` необязательны, но если используется хотя бы одна из этих переменных, нужно задать все три. При `npm run db:setup` или `npm run db:seed` пользователь с таким email создаётся с ролью `admin`. Если пользователь уже существует, ему назначается роль `admin`, а его текущий пароль не меняется. Обычная регистрация через сайт всегда создаёт роль `user`.

Если в пароле базы есть `@`, `:`, `/`, `#`, `%`, кодируйте их как компоненты URL. Например, `@` → `%40`. Никогда не добавляйте к `DATABASE_URL` префикс `VITE_`. Реальные `ADMIN_PASSWORD` и пароли базы должны храниться только в `.env`, а не в `.env.example`.

3. Создайте таблицы и загрузите исходные сценарии:

```powershell
npm run db:setup
```

Команду можно выполнять повторно: применённые миграции и существующие сценарии не перезаписываются. Она не создаёт саму базу и пользователя — это сделано на шаге 1.

4. Запустите приложение:

```powershell
npm run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Команда запускает Vite и Node API вместе. Сервер API работает на порту 3001. Если `ADMIN_*` были настроены до `db:setup`, можно сразу войти под указанным администратором. Остальные пользователи регистрируются через обычную форму и получают роль `user`. После входа администратора панель управления доступна по адресу `/admin`, а старые маршруты `/editor` пока сохранены для обратной совместимости.

## Полный запуск через Docker

Для обычного запуска локальные Node.js и PostgreSQL не нужны: приложение и база запускаются через Docker Compose. PostgreSQL находится во внутренней сети Docker и хранит данные в постоянном томе `cool_peppers_postgres`. При каждом старте приложения миграции и начальные сценарии применяются автоматически.

1. Создайте локальный файл настроек:

```powershell
Copy-Item .env.example .env
```

Обязательно поменяйте `POSTGRES_PASSWORD`. Если нужен заранее созданный супер-администратор, также задайте `ADMIN_NAME`, `ADMIN_EMAIL` и `ADMIN_PASSWORD`.

2. Соберите и запустите весь проект:

```powershell
docker compose up -d --build
```

3. Проверьте состояние:

```powershell
docker compose ps
docker compose logs -f app
```

После статуса `healthy` откройте [http://127.0.0.1:3001](http://127.0.0.1:3001). Обычная остановка контейнеров не удаляет базу:

```powershell
docker compose down
```

Не используйте `docker compose down -v`, если хотите сохранить текущую БД: ключ `-v` удаляет том PostgreSQL.

### Резервные копии PostgreSQL

Бэкапы создаются в формате PostgreSQL custom dump (`.dump`) и сразу попадают в обычную папку проекта `backups/`. Рядом сохраняется файл `.sha256` для проверки целостности. Поэтому резервную копию можно просто скопировать с компьютера, положить в архив или перенести на другой сервер — она не заперта внутри Docker volume.

Создать бэкап без остановки приложения:

```powershell
docker compose run --rm backup
```

После выполнения появятся файлы вида:

```text
backups/arena_20260928T120000Z.dump
backups/arena_20260928T120000Z.dump.sha256
```

Если на компьютере установлен Node.js, доступны короткие команды:

```powershell
npm run docker:backup
npm run docker:backups
```

Восстановление заменяет текущее содержимое базы содержимым выбранного dump. На время восстановления приложение необходимо остановить, чтобы оно не выполняло запросы к изменяемой БД:

```powershell
docker compose stop app
$env:BACKUP_FILE = "arena_20260928T120000Z.dump"
docker compose run --rm restore
docker compose up -d app
Remove-Item Env:BACKUP_FILE
```

Более безопасный вариант при установленном Node.js сам останавливает и запускает `app`:

```powershell
npm run docker:restore -- latest
# или
npm run docker:restore -- arena_20260928T120000Z.dump
```

`latest` выбирает последний `.dump` из папки `backups`. При ошибке восстановления приложение намеренно остаётся остановленным, чтобы не работать с частично восстановленной базой.

### Доступ к PostgreSQL с хоста

В основном `compose.yaml` порт PostgreSQL наружу не публикуется — приложению база доступна как `postgres:5432` внутри сети Docker, поэтому локальный PostgreSQL на 5432 не конфликтует с проектом. Для отладки через psql/pgAdmin можно временно добавить override:

```powershell
docker compose -f compose.yaml -f compose.db-port.yaml up -d
```

Тогда PostgreSQL будет доступен на `127.0.0.1:${POSTGRES_PORT:-5432}`.

### Полный сброс локальной Docker-БД

Только если данные больше не нужны или уже сохранён бэкап:

```powershell
docker compose down -v
docker compose up -d --build
```

При следующем старте приложение создаст чистую схему миграциями и загрузит начальные данные.

## Сборка и запуск одним сервером

```powershell
npm run build
npm start
```

Откройте [http://127.0.0.1:3001](http://127.0.0.1:3001). API также раздаёт собранный SPA с поддержкой прямых ссылок. `npm run preview` — только просмотр сборки клиента; API всё равно должен работать.

Для размещения за HTTPS задайте `APP_ORIGIN` с фактическим адресом сайта и `COOKIE_SECURE=true`. Разработка по обычному HTTP использует `COOKIE_SECURE=false`. Статический хостинг без Node API и PostgreSQL больше не является достаточным способом запуска. Старые `vercel.json` и `public/_redirects` не развёртывают сервер или базу.

## Редактор и версии

1. Войдите как администратор и откройте `/admin/scenarios`.
2. Выберите «Пустой сценарий» или готовую основу. «Создать копию» не меняет исходную публикацию.
3. Добавляйте реплики, реакции и финалы. Свойства выбранного блока находятся справа. Персонажи, этапы и основная информация доступны слева.
4. Потяните точку реакции к карточке или в пустое место. Во втором случае выберите новую реплику или финал. Переход также можно назначить через Inspector.
5. «Сохранить» вручную записывает граф и расположение блоков в личный черновик. Пустые реплики и незавершённые связи сохранять можно. Автосохранения пока нет.
6. «Проверить» показывает ошибки и предупреждения. Нажатие на пункт выделяет соответствующий блок. Недостижимые блоки — предупреждение; закрытая петля без пути к финалу — ошибка.
7. «Тестировать» запускает текущий черновик с выбором реакций кнопками. Реальные попытки и статистика не создаются.
8. «Опубликовать» проверяет граф и создаёт неизменяемую версию. Начатые попытки остаются на прежней версии. Обычный игрок проходит новые сценарии через существующие страницы тренировки и результата.
9. «В архив» в списке убирает сценарий из каталога, сохраняя историю. Повторная публикация возвращает его.

Оценка каждой реакции настраивается одним `penalty`: `0` — уместная, `1` — сомнительная, `2` — нежелательная; пояснение хранится в `feedback`. В настройках сценария можно включить общий penalty-финал и выбрать автоматически рассчитанный или ручной лимит. Недостижимый лимит блокирует публикацию. Старые поля оценки при импорте автоматически преобразуются в текущую модель.

### Импорт и экспорт JSON

В разделе «Настройки → JSON сценария» можно импортировать файл в текущий черновик или скачать текущую структуру. Рекомендуемый переносимый формат — `arena-scenario` версии `2`; пример находится в `docs/arena-scenario-template.json`, описание полей — в `docs/SCENARIO_JSON_FORMAT.md`. Импорт также понимает старый полный экспорт (`preview + definition + editor`) и чистую текущую `MakerDefinition` с `schemaVersion: 3` и старые definition v2. При импорте ID текущего сценария в базе не меняется, а сам импорт можно отменить через Ctrl+Z.

При конфликте двух вкладок сервер возвращает 409 и не перезаписывает чужие изменения. Ваш вариант остаётся на экране. Скачайте его через «Настройки → JSON сценария → Скачать JSON», затем обновите страницу и при необходимости импортируйте файл обратно. Перед уходом с несохранёнными изменениями есть предупреждение. Undo/redo хранит последние 50 правок в текущей вкладке.


## Геймификация

После завершения сценария сервер начисляет XP, прогресс навыка и мастерство 1–3 ★. Первое прохождение и новая концовка дают полную рассчитанную награду; повтор уже открытой концовки — 35%, поэтому один и тот же путь нельзя бесконечно фармить с полной эффективностью. Уровень и прогресс показываются в профиле; в закрытом состоянии меню аккаунта в header XP и уровень не выводятся, а внутри раскрытого меню остаётся компактная строка уровня.

Администратор может создавать, редактировать, активировать и архивировать достижения на `/admin/achievements`. Новые активные правила ретроактивно проверяются по истории пользователей; архивирование не отбирает уже полученные достижения. Подробности — в [docs/GAMIFICATION.md](docs/GAMIFICATION.md). После обновления существующей базы выполните `npm run db:migrate` для применения `006_gamification.sql`.

## Тесты

Без базы:

```powershell
npm run typecheck
npm run test:logic
npm run test:api:embedded
npm run build
```

`test:api:embedded` использует PGlite — PostgreSQL в WebAssembly. Это проверка SQL и поведения API, а не полноценная проверка сетевого подключения, ролей и параллельных транзакций PostgreSQL.

Полная интеграционная проверка с PostgreSQL:

```sql
CREATE DATABASE arena_test OWNER arena;
```

```powershell
$env:TEST_DATABASE_URL = "postgresql://arena:change_me@127.0.0.1:5432/arena_test"
npm run test:api
```

Тесты создают уникальную схему `arena_test_<uuid>` и удаляют только её. Пользователю тестовой базы нужны права `CREATE SCHEMA`. Без `TEST_DATABASE_URL` команда завершается с понятной ошибкой, а не пропускает проверку.

Для браузерных тестов настройте отдельную тестовую базу в `DATABASE_URL`, выполните `db:setup`, затем:

```powershell
npm run build
npx playwright install chromium
npm run test:ui
```

Playwright сам запускает API и preview, если они не запущены. Браузерные тесты создают тестовые аккаунты и сценарии, поэтому запускайте их на тестовой базе. `npm test` последовательно запускает unit, PostgreSQL API и UI тесты; для него нужны обе настроенные строки подключения и браузер.

Для браузерной проверки на временной встроенной базе (без установленного PostgreSQL):

```powershell
npm run build
npx playwright install chromium
npm run test:ui:embedded
```

Остановите обычный сервер на порту 3001 перед этой командой. Тестовый сервер создаёт отдельную базу PGlite в памяти и тестового администратора; после тестов база исчезает. Этот сервер не используется в `npm run dev` или `npm start`.

## Если не запускается

- **`ECONNREFUSED ...:5432`**: PostgreSQL не запущен или в строке подключения неверен порт.
- **`password authentication failed`**: проверьте имя пользователя, пароль и кодирование специальных символов в URL.
- **`relation schema_migrations does not exist`**: выполните `npm run db:setup` с той же `DATABASE_URL`.
- **«API недоступен»**: запускайте `npm run dev`, а не только `npm run dev:web`. Порт API должен совпадать с `API_PORT`.
- **403 при сохранении**: адрес браузера должен входить в `APP_ORIGIN`. Для localhost и 127.0.0.1 значения уже перечислены в `.env.example`.
- **Сразу выходит из аккаунта при HTTP**: проверьте `COOKIE_SECURE=false`. Не переключайтесь между localhost и 127.0.0.1 во время одной сессии.
- **`Missing script: dev`**: терминал открыт не в папке с `package.json` из этого архива.

Контактная форма в футере по-прежнему обозначена как недоступная. Отзывы о завершённых тренировках работают. Подтверждение email, сброс пароля и социальный вход в этот этап не входят.

## Информационные страницы и обращения

Страницы `/about` и `/feedback` доступны по ссылкам в футере. Отправленные через форму сообщения сохраняются в PostgreSQL и доступны администраторам на `/admin/messages`.

После переноса выполните `npm run db:migrate` (новая миграция `005_contact_messages.sql`), затем `npm run build` и перезапустите приложение. Сборка также создаёт готовый HTML этих двух страниц. Подробности API, настройки `VITE_SITE_URL` и проверки — в [docs/INFO-PAGES.md](docs/INFO-PAGES.md).
