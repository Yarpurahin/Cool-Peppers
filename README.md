# Арена переговоров — PostgreSQL, версия 0.3.0

React SPA теперь работает через серверный API с PostgreSQL. Браузер не подключается к базе напрямую. Пароли базы находятся только в `.env` на сервере.

Реализованы регистрация и вход, сохранение профиля, каталог из базы, личные попытки, история ответов, результаты, отзывы, черновики редактора, публикация версий и архивирование сценариев. При перезапуске тренировки старая попытка остаётся в истории. Старый результат всегда использует ту версию вопросов, по которой пользователь проходил тренировку.

В исходном архиве один исполняемый сценарий: `terms` («Переговоры об условиях работы»). `new-deadline` и `feedback` — демонстрационные макеты. Они также хранятся в PostgreSQL, но реальные оценки для них не придуманы. Для новой тренировки в редакторе создайте копию исполняемого сценария.

## Запуск на Windows с установленным PostgreSQL

Потребуются Node.js **22.12+** (рекомендуется 24) и PostgreSQL **16+**. Все команды npm запускайте из папки, содержащей `package.json`.

1. Откройте SQL Shell (psql) или Query Tool в pgAdmin под администратором PostgreSQL. Создайте отдельного пользователя приложения и базу:

```sql
CREATE ROLE arena WITH LOGIN PASSWORD 'change_me';
CREATE DATABASE arena OWNER arena;
```

Замените `change_me` своим паролем. `CREATE DATABASE` выполняйте отдельно от транзакции. Если база и пользователь уже существуют, повторно создавать их не нужно.

2. В PowerShell, в папке проекта:

```powershell
Copy-Item .env.example .env
npm ci
```

Откройте `.env` и задайте свою строку подключения:

```dotenv
DATABASE_URL=postgresql://arena:change_me@127.0.0.1:5432/arena
```

Если в пароле есть `@`, `:`, `/`, `#`, `%`, кодируйте их как компоненты URL. Например, `@` → `%40`. Никогда не добавляйте к этой переменной префикс `VITE_`.

3. Создайте таблицы и загрузите исходные сценарии:

```powershell
npm run db:setup
```

Команду можно выполнять повторно: применённые миграции и существующие сценарии не перезаписываются. Она не создаёт саму базу и пользователя — это сделано на шаге 1.

4. Запустите приложение:

```powershell
npm run dev
```

Откройте [http://127.0.0.1:5173](http://127.0.0.1:5173). Команда запускает Vite и Node API вместе. Сервер API работает на порту 3001. Зарегистрируйте свой аккаунт: заранее созданного пользователя и общего пароля нет.

## Вариант с Docker: только база

Если PostgreSQL не установлен, можно запустить его через Docker Desktop. Node.js всё равно запускается локально.

```powershell
Copy-Item .env.example .env
# Укажите один и тот же пароль в POSTGRES_PASSWORD и DATABASE_URL.
docker compose up -d
npm ci
npm run db:setup
npm run dev
```

В `compose.yaml` используется PostgreSQL 17 и постоянный именованный том. При первом старте дождитесь готовности: `docker compose ps`. Если порт 5432 уже занят, задайте `POSTGRES_PORT=5433` и укажите 5433 в `DATABASE_URL`.

Остановка базы: `docker compose stop`. Изменение `POSTGRES_PASSWORD` после первого запуска не меняет пароль уже созданного пользователя — меняйте его через `ALTER ROLE`. Не удаляйте том, если хотите сохранить данные.

## Сборка и запуск одним сервером

```powershell
npm run build
npm start
```

Откройте [http://127.0.0.1:3001](http://127.0.0.1:3001). API также раздаёт собранный SPA с поддержкой прямых ссылок. `npm run preview` — только просмотр сборки клиента; API всё равно должен работать.

Для размещения за HTTPS задайте `APP_ORIGIN` с фактическим адресом сайта и `COOKIE_SECURE=true`. Разработка по обычному HTTP использует `COOKIE_SECURE=false`. Статический хостинг без Node API и PostgreSQL больше не является достаточным способом запуска. Старые `vercel.json` и `public/_redirects` не развёртывают сервер или базу.

## Что где находится

| Путь                                               | Назначение                                                        |
| -------------------------------------------------- | ----------------------------------------------------------------- |
| `server/migrations/001_initial.sql`                | Таблицы, ограничения, индексы, защита опубликованных версий       |
| `server/db.ts`                                     | Пул соединений `pg` и транзакции                                  |
| `server/migrate.ts`                                | Миграции с контрольной суммой и блокировкой параллельного запуска |
| `server/seed.ts`                                   | Первоначальная загрузка трёх сценариев из исходных файлов         |
| `server/app.ts`                                    | HTTP API и проверка доступа                                       |
| `server/auth.ts`                                   | Хеширование паролей и серверные сессии                            |
| `server/store.ts`                                  | Чтение попыток и конкретных версий сценариев                      |
| `src/types/validation.ts`                          | Проверка формата документов и входных данных                      |
| `src/api/client.ts`                                | Запросы интерфейса к API                                          |
| `src/app/DataProvider.tsx`                         | Аккаунт и каталог из базы                                         |
| `src/features/negotiation/NegotiationProvider.tsx` | Работа интерфейса с сохранёнными попытками                        |
| `src/features/negotiation/model/engine.ts`         | Существующие правила переходов и оценки, используемые сервером    |
| `docs/DATABASE.md`                                 | Модель данных, соответствие типов и предложения по расширению     |
| `docs/API.md`                                      | Маршруты, форматы запросов и ответы                               |
| `docs/VERIFICATION.md`                             | Выполненная проверка и ограничения среды                          |

Файлы `src/data/scenarios.ts` и `features/negotiation/data/employment.ts` используются как начальные данные. После `db:seed` приложение читает опубликованные версии из базы. Изменение исходного TS-файла не перезаписывает уже загруженную версию: создавайте и публикуйте новую через редактор.

Старый `attemptRepository.ts` оставлен для проверки восстановления прежнего формата в существующих unit-тестах. В работающем интерфейсе localStorage больше не используется. Автоматического переноса старых анонимных попыток в новый аккаунт нет. Демонстрационные записи `src/data/profile.ts` не попадают в базу и не выдаются за реальные результаты.

## Редактор и версии

1. Войдите и откройте «Редактор».
2. Выберите основу и нажмите «Создать копию». Чужие и исходные сценарии напрямую редактировать нельзя.
3. Измените описание, вопросы, ответы, переходы, штрафы и разборы. Во вкладке JSON доступны также персонажи, этапы, концовки, варианты реплик и полная конфигурация.
4. «Сохранить» записывает личный черновик. Синтаксис и структура проверяются, но незавершённые связи допустимы до публикации.
5. «Опубликовать» сохраняет черновик, проверяет граф и создаёт неизменяемую версию, доступную всем пользователям этой установки. Начатые попытки остаются на прежней версии.
6. «В архив» убирает сценарий из каталога. История и результаты сохраняются. Повторная публикация возвращает его в каталог.

При конфликте правок в двух вкладках сервер вернёт 409 и не перезапишет чужие изменения. Скопируйте свой вариант из JSON, обновите страницу и объедините правки.

## Тесты

Без базы:

```powershell
npm run typecheck
npm run test:logic
npm run test:api:embedded
npm run build
```

`test:api:embedded` использует PGlite — PostgreSQL в WebAssembly. Это проверка SQL и поведения API, а не полноценная проверка сетевого подключения, ролей и параллельных транзакций PostgreSQL.

Полная интеграционная проверка с PostgreSQL:

```sql
CREATE DATABASE arena_test OWNER arena;
```

```powershell
$env:TEST_DATABASE_URL = "postgresql://arena:change_me@127.0.0.1:5432/arena_test"
npm run test:api
```

Тесты создают уникальную схему `arena_test_<uuid>` и удаляют только её. Пользователю тестовой базы нужны права `CREATE SCHEMA`. Без `TEST_DATABASE_URL` команда завершается с понятной ошибкой, а не пропускает проверку.

Для браузерных тестов настройте отдельную тестовую базу в `DATABASE_URL`, выполните `db:setup`, затем:

```powershell
npm run build
npx playwright install chromium
npm run test:ui
```

Playwright сам запускает API и preview, если они не запущены. Браузерные тесты создают тестовые аккаунты и сценарии, поэтому запускайте их на тестовой базе. `npm test` последовательно запускает unit, PostgreSQL API и UI тесты; для него нужны обе настроенные строки подключения и браузер.

## Если не запускается

- **`ECONNREFUSED ...:5432`**: PostgreSQL не запущен или в строке подключения неверен порт.
- **`password authentication failed`**: проверьте имя пользователя, пароль и кодирование специальных символов в URL.
- **`relation schema_migrations does not exist`**: выполните `npm run db:setup` с той же `DATABASE_URL`.
- **«API недоступен»**: запускайте `npm run dev`, а не только `npm run dev:web`. Порт API должен совпадать с `API_PORT`.
- **403 при сохранении**: адрес браузера должен входить в `APP_ORIGIN`. Для localhost и 127.0.0.1 значения уже перечислены в `.env.example`.
- **Сразу выходит из аккаунта при HTTP**: проверьте `COOKIE_SECURE=false`. Не переключайтесь между localhost и 127.0.0.1 во время одной сессии.
- **`Missing script: dev`**: терминал открыт не в папке с `package.json` из этого архива.

Контактная форма в футере по-прежнему обозначена как недоступная. Отзывы о завершённых тренировках работают. Подтверждение email, сброс пароля и социальный вход в этот этап не входят.
