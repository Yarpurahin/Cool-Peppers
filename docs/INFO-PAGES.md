# «О проекте» и «Обратная связь»

## Дизайн и содержание

Сохранены Manrope, молочный фон, зелёный и терракотовый акценты, радиусы, ширина контейнера и адаптивная навигация. Переиспользованы `Layout`, `Header`, `Footer`, `Button`, `ButtonLink`, `Icon`, классы `panel`, `field`, `form-stack`, `section-heading` и иллюстрация главной страницы. Дополнительные стили находятся в `src/styles/info-pages.css`.

`/about` объясняет назначение тренажёра обычным языком: подготовка к важным разговорам, выбор подхода, разбор собственных решений. Страница содержит вводный блок, цель проекта, три возможности, три шага тренировки и приглашение попробовать. Текст не обещает отсутствующие сценарии, гарантированные результаты или общение с живым экспертом.

`/feedback` использует две колонки: краткая информация о команде и темах обращений слева, форма справа. На небольших экранах блоки располагаются последовательно. Три обязательных поля: тема, email для ответа и сообщение. Не запрашиваются телефон, имя, адрес и другие лишние данные. Реальные email и соцсети команды в исходниках отсутствуют, поэтому вымышленные контакты и сроки ответа не добавлены. Ниже формы — три раскрывающихся ответа на частые вопросы.

## Работа формы

- Отправка без регистрации: `POST /api/contact`.
- Проверка одной Zod-схемой на клиенте и сервере: корректный email, тема из списка, 20–3000 символов текста после удаления пробелов по краям.
- Сохранение в `contact_messages`, отдельной от отзывов о тренировках. Миграция `005_contact_messages.sql` применяется обычной командой `npm run db:migrate`.
- Во время отправки поля и кнопка блокируются. Повторный запрос с тем же `requestId` не создаёт дубль, в том числе при потере ответа сервера. Изменённое сообщение получает новый идентификатор.
- Подтверждение с номером обращения появляется только после успешного ответа API. При ошибке текст сохраняется в форме, сообщение об ошибке объясняет дальнейшее действие.
- Используются существующие проверки JSON и источника запроса. Лимит — пять запросов с одного IP за 15 минут, включая невалидные. Он хранится в памяти одного процесса, как лимит авторизации; при нескольких экземплярах API нужен общий ограничитель на шлюзе. За обратным прокси следует настроить его лимитирование, чтобы посетители не разделяли один IP приложения.
- `GET /api/admin/messages?offset=0` доступен только администратору. `/admin/messages` показывает по 30 обращений, новые сверху, с обновлением и переходами между страницами.
- «Ответить» открывает письмо в настроенной почтовой программе администратора. Сайт сам не отправляет email и не создаёт почтовый ящик. Оповещения о новых сообщениях не подключены: входящие проверяются в админке.

Сообщения хранятся до удаления администратором базы. Перед публичным запуском владелец проекта определяет срок хранения и публикует собственные сведения об обработке данных; в интерфейсе уже объяснено, для чего нужен email и кому доступно сообщение.

## Семантика и доступность

- Один `h1`, последовательная иерархия заголовков, `main`, `nav`, `section`, `aside`, списки, настоящие ссылки для переходов.
- Общий skip-link и перенос фокуса на `main` при смене маршрута. Активные ссылки имеют `aria-current`.
- Кнопки, ссылки и раскрывающиеся вопросы доступны с клавиатуры, имеют hover и видимый focus. Сохранена поддержка `prefers-reduced-motion`.
- Видимые `label`, `required`, `autocomplete="email"`, нативный `select`, пояснения через `aria-describedby` и ошибки через `aria-invalid`.
- После невалидной отправки фокус переходит в первое ошибочное поле; после успешной — на подтверждение с `role="status"`. Ошибка API объявляется через `role="alert"`. Сетевые ошибки также обрабатывает общий попап приложения.
- FAQ использует нативные `details`/`summary`. Декоративные иконки скрыты от скринридеров. У иллюстрации есть описание и заданные размеры.
- Обе публичные страницы отображаются при недоступном API. Отправить форму без работающего API нельзя; интерфейс явно сообщает об этом.

## SEO и сборка

Существующий стек сохранён: React 19, TypeScript, Vite, React Router, Express и PostgreSQL. Зависимости проекта не менялись.

`npm run build` проверяет типы, собирает клиент и запускает `scripts/prerender.mjs`. Скрипт собирает временный SSR-модуль, рендерит настоящее React-дерево и создаёт `dist/about/index.html` и `dist/feedback/index.html`; временная директория удаляется. Браузер гидратирует этот HTML. Express отдаёт его непосредственно по `/about` и `/feedback`, включая прямой вход и перезагрузку. Остальные маршруты сохраняют существующее поведение SPA.

Для каждой страницы заданы уникальные title/description, Open Graph, Twitter metadata и JSON-LD типа `AboutPage` или `ContactPage`. При переходах внутри SPA метаданные обновляются; JSON-LD информационных страниц удаляется при уходе с них. Существующие метаданные сценариев и запрет индексации закрытых страниц сохранены. Тексты доступны в исходном HTML без выполнения JavaScript. Форма требует JavaScript, о чём есть `noscript`-пояснение.

`VITE_SITE_URL` — публичный origin вида `https://ваш-домен`, без пути, параметров и логина. Укажите реальное значение в `.env` **до сборки**. Тогда генерируются абсолютные canonical, `og:url`, URL в JSON-LD и `dist/sitemap.xml`. Без адреса они не добавляются в статический HTML; после запуска JavaScript canonical строится по текущему origin браузера. `robots.txt` создаётся при каждой сборке. Закрытые разделы защищены авторизацией; robots.txt не является механизмом контроля доступа.

Поисковая индексация не гарантируется самим наличием метаданных. Базовые рекомендации: [Google Search Central — JavaScript SEO](https://developers.google.com/search/docs/crawling-indexing/javascript/javascript-seo-basics), [W3C WAI — формы](https://www.w3.org/WAI/tutorials/forms/).

## Проверка

Чтобы быстро посмотреть только новые страницы без базы: `npm ci`, затем `npm run dev:web`, после чего откройте `http://127.0.0.1:5173/about` или `http://127.0.0.1:5173/feedback`. Для отправки обращений и просмотра входящих нужны API и база по основной инструкции README.

```powershell
npm run build
npm run test:api:embedded
# Браузерные проверки новых страниц и существующей навигации:
npx playwright install chromium
$env:PGLITE_UI = "1"
npx playwright test tests/info-pages.spec.ts tests/interface.spec.ts
```

Браузерные проверки используют временную базу и не требуют установленного PostgreSQL. Остановите обычный API на 3001 перед запуском. В Linux/macOS переменную можно задать перед командой: `PGLITE_UI=1 npx playwright test tests/info-pages.spec.ts tests/interface.spec.ts`.

Добавлены проверки адаптивности на 320/390/768/1440 px, доступности страниц при отказе API, клавиатурной навигации, обновления SEO, HTML до запуска JavaScript, ошибок и успешной отправки, просмотра реального сообщения в админке. API-тест проверяет валидацию, нормализацию email, сохранение, идемпотентный повтор, ограничение запросов и права доступа.

## Перенос в актуальную версию

Основа патча — `Cool-Peppers (2)(1).zip`; страницы и логика обращений перенесены из `Cool-Peppers-develop(10) (1).zip`.

```bash
git switch -c feature/about-feedback
git apply --check about-feedback-transfer.patch
git apply about-feedback-transfer.patch
npm run db:migrate
npm run build
```

После применения перезапустите приложение. Коммит и отправка изменений выполняются вручную.

Миграции 001–004, аккаунты, аватары, сценарии, редактор, восстановление черновиков и обработка 404/500 сохранены. Новые страницы используют текущую тему; её и общий попап ошибок адаптировали к генерации HTML без браузера. Ссылки доступны в футере, обращения — в навигации администратора.

Этот патч переносит существующие страницы и функциональность. Изменение содержания страницы «О проекте», анимация FAQ, новая палитра, оформление элементов и управление дополнительными администраторами относятся к следующему этапу.
