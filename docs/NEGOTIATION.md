# Прохождение переговорного сценария

Исполняемый формат сценария един для maker, публикации, API и проигрывателя: `MakerDefinition` (`schemaVersion: 3`). Отдельной runtime-модели с `speakerId / answers / next` больше нет.

## Каноническая модель

- реплика: `characterId`, `text`, `reactions[]`;
- реакция пользователя: `id`, `intent`, `label`, `examples`, `penalty`, `feedback` и ровно один переход (`nextNodeId` или `endingId`);
- оценка: `penalty` (`0 | 1 | 2`) и `feedback`;
- контекстный вариант текста: `textVariants[].afterReactionId`;
- финал: `success / neutral / failure`;
- режим учебной обратной связи: `settings.feedbackMode = immediate | summary | hidden`.

`intent` и `examples` уже являются частью канонической модели и сохраняются для будущего AI-классификатора. Кнопочный режим использует тот же путь исполнения, что позже будет использовать распознанный intent.

## Движок

`src/features/negotiation/model/engine.ts` компилирует `MakerDefinition` напрямую. Он:

- проверяет ссылки между репликами, реакциями, персонажами и финалами;
- допускает циклы только если из них существует путь к финалу;
- ограничивает одну попытку 500 подтверждёнными реакциями;
- выбирает контекстный текст по последней реакции;
- считает штрафы только из `reaction.penalty`;
- не читает координаты maker и `preview`.

`presentation.ts` строит экран прохождения и итоговый разбор непосредственно из того же графа. Второй копии сценария для UI нет.

## Сохранение попыток

Браузер не хранит рабочую попытку в `localStorage`. Источник истины — PostgreSQL:

- `attempts` — состояние попытки;
- `attempt_answers` — подтверждённая история;
- `feedback` — отзыв после завершения;
- `attempt_rewards` — единственная награда геймификации за попытку.

`NegotiationProvider` получает и изменяет состояние только через API. Это исключает старую схему, где браузер мог хранить отдельную копию прогресса.

## Совместимость старых сценариев

Legacy-форматы поддерживаются только на границе чтения:

- старый runtime JSON (`speakerId / answers / next`);
- старый maker v2 с `reaction.legacy` / `settings.legacyFailure`;
- очень старый `preview.dialogue / preview.example`.

`src/features/maker/model/compatibility.ts`, `legacySchema.ts` и `src/types/validation.ts` преобразуют их в текущий `MakerDefinition`. После преобразования остальное приложение legacy-поля больше не видит.

Для существующей БД предусмотрено:

```bash
npm run db:normalize-scenarios
```

Команда переписывает сериализацию старых версий и черновиков в канонический формат, сохраняя ID сценариев, номера публикаций и смысл графа. В обычной работе опубликованные версии остаются неизменяемыми; нормализатор — контролируемая служебная операция миграции формата.

Docker выполняет нормализацию при старте после миграций и seed.

## Общий penalty-финал

Каноническая настройка — `settings.penalty = { enabled, threshold, failureEndingId }`. После каждой реакции движок добавляет `reaction.penalty`. Явный `reaction.endingId` имеет приоритет; общий failure-финал используется только если сюжетного финала нет и накопленная сумма достигла `threshold`.

Maker анализирует достижимые состояния графа и предлагает строгий, рекомендуемый и мягкий пороги. Недостижимый включённый threshold является ошибкой публикации. Старые `failureRule`, `legacyFailure` и переходный `penaltyRule` поддерживаются только на границе импорта.

## Что удалено как legacy

- отдельный `ScenarioDefinition` runtime;
- `DialogueNode / AnswerOption / Transition` старого движка;
- `toRuntimeDefinition()`;
- runtime-реестр встроенных сценариев;
- клиентский `attemptRepository` и сохранение попытки в `localStorage`;
- глобальный `DemoProvider`, который больше никем не использовался;
- исполняемые `preview.dialogue` и `preview.example`;
- пользовательские надписи про «оценку из исходного сценария».

Compatibility-parser остаётся намеренно, чтобы импорт старых JSON и обновление существующей БД не ломали данные.
