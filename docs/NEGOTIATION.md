# Прохождение переговорного сценария

Реализован сценарий «Переговоры об условиях работы» из предоставленного DOCX.
URL: `/scenarios/terms`. Остальные два сценария остаются демонстрационными.
Редактор и авторизация остаются заглушками; редактор не меняет рабочие данные.

## Порядок применения

Основа — содержимое `Cool-Peppers.zip`, коммит `64bc0456c86d0c79c443c6b8c8e0f38060b5648c`.
Патчи содержат два последовательных коммита. Применять из корня чистого проекта:

```bash
git switch -c feature/negotiation-ui
git am /path/to/01-negotiation-ui.patch
npm run build

git switch -c feature/negotiation-engine
git am /path/to/02-negotiation-engine.patch
npm run build
npm run test:logic
npm run test:ui
```

Если зависимости ещё не установлены, сначала выполнить `npm ci`.
Для браузерных тестов нужен Chromium: `npx playwright install chromium`.
Можно передать путь к установленному браузеру через `PW_EXECUTABLE_PATH`.
Для отдельного PR интерфейса выбрать базовую ветку проекта, для PR логики —
`feature/negotiation-ui`. После слияния интерфейса базу второго PR можно сменить.
Второй патч не предназначен для применения к исходному архиву без первого.

## Что изменено в предварительной типизации

- `Transition` — объединение `{ type: 'node'; nodeId }` и
  `{ type: 'ending'; endingId }`. Нельзя одновременно указать обе цели или ни одной.
- Есть явный `startNodeId`, версия сценария и отдельные этапы с названиями.
- `ScenarioAttempt` — объединение незавершённой и завершённой попытки.
  У активной обязателен вопрос, у завершённой — концовка и время завершения.
- Контекстные варианты реплики привязаны к ID предыдущего ответа, поэтому
  вопрос 3 остаётся одним вопросом, а не двенадцатью копиями под разные ветки.
- Роли персонажей — произвольные строки: модель подходит не только для
  кандидата и работодателя. Несколько собеседников поддерживаются через `speakerId`.
- `penalty` и `feedback` принадлежат ответу. Итог строится по реальным решениям.
- ID — обычные смысловые алиасы строк. В исходном предложении они также не были
  branded-типами, несмотря на формулировку в таблице.
- Убраны пока не используемые `User`, `HiddenUserData`, `GameSession`,
  `maxAttempts`, `ScenarioTone`, `ScenarioStatus`, `FeedbackTemplate`,
  `selectedPackages`, зарплатные метрики и флаги. Авторизация, публикация и
  административные ограничения должны получить собственные модели, когда
  появятся соответствующие API и поведение.
- Не добавлены пока неиспользуемые условия доступности. Предложенный
  `StateCondition` разрешал некорректные сочетания: отсутствие обоих ключей,
  одновременно metric и flag, сравнение числа с boolean. При появлении такой
  задачи его следует вводить как дискриминируемое объединение условий с
  ограниченными ключами, а не набор необязательных полей.
- Старый тип оформления переименован в `ScenarioPreview`, а демонстрационный
  вопрос редактора — в `DemoDialogueNode`, чтобы не путать их с рабочим графом.

## Правила прохождения и оценки

Пользователь сначала выбирает реплику, затем подтверждает её кнопкой «Ответить».
Выбор определяет следующий вопрос. Штрафы не меняют обычные переходы, но при
достижении порога провал имеет приоритет над переходом и обычной концовкой.

Порог: `Math.ceil(число всех уникальных достижимых вопросов / 2)`.
В текущем сценарии это `Math.ceil(11 / 2) = 6`. Варианты текста одного вопроса
не увеличивают количество вопросов. Каждый путь содержит четыре ответа,
поэтому максимум штрафов за текущую попытку — 4 и провал недостижим.
Это намеренное следствие согласованного правила, а не порога по длине пути.
Механика провала проверяется на отдельных тестовых сценариях.

В каждом вопросе ровно один ответ получает +1, остальные — 0. Метки заданы
постоянно в данных и не выбираются случайно при запуске. Оценка временная;
все исходные реплики могут быть уместны в реальных переговорах. Об этом
сообщается перед началом и в разборе, чтобы учебная заглушка не воспринималась
как экспертная рекомендация. Пояснения к ответам добавлены для тренировки;
они не являются частью исходного DOCX.

| Вопрос DOCX | Временный штрафной ответ |
| ----------- | ------------------------ |
| 1           | 1.4                      |
| 2А          | 2А.2                     |
| 2Б          | 2Б.3                     |
| 2В          | 2В.3                     |
| 2Г          | 2Г.3                     |
| 3           | 3.1                      |
| 4А          | 4А.1                     |
| 4Б          | 4Б.2                     |
| 4В          | 4В.3                     |
| 4Г-1        | 4Г-1.3                   |
| 4Г-2        | 4Г-2.3                   |

Успешная концовка — переход к письменному предложению после 4А.1, 4А.2,
4Б.1, 4Б.2 или 4В.1. Остальные финальные ответы требуют дополнительного
обсуждения и дают нейтральную концовку. Второй раунд не запускается.
Согласие рассмотреть письменное предложение не объявляется подписанным договором.

На экране результата круг показывает фактические штрафы и порог, а не
выдуманный рейтинг из 100. Разбор включает только выбранные ответы,
соответствующие им реплики собеседника и пояснения.

## Сохранение — версия 0.3.0

Попытки и отзывы сохраняются через API в PostgreSQL. Подтверждённый ответ
фиксируется вместе с новым состоянием попытки в одной транзакции. Интерфейс
переходит к следующему вопросу только после успешного ответа сервера.

Каждая попытка привязана к неизменяемой версии сценария. Редактирование и
публикация новой версии не меняют старую историю. Повторное прохождение
создаёт новую запись; старые результаты доступны в профиле. Пользователь
видит только свои попытки и отзывы.

При ошибке сети выбранный ответ остаётся на экране для повторной отправки.
После перезагрузки интерфейс запрашивает прогресс из базы. `localStorage`
больше не является рабочим хранилищем; прежний адаптер оставлен только для
проверок старого формата в unit-тестах.

## Развитие

1. Утвердить оценку реплик и пояснения, при необходимости пересмотреть порог.
   Достаточно изменить данные и функцию вычисления порога, UI не зависит от рубрики.
2. Добавить сценарии как новые определения и зарегистрировать их. Для появления
   в каталоге потребуется их проекция; движок и экраны остаются общими.
3. При расширении редактора можно добавить совместные права и журнал изменений.
   Сервер, пользователи, архив попыток, версии и конфликты черновиков уже реализованы.
4. Для повторяемых узлов потребуются лимиты посещений и отдельно согласованное
   правило подсчёта вопросов; текущий движок поддерживает конечные графы без циклов.
